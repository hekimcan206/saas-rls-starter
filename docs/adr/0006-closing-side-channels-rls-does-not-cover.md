# 6. Side channels RLS does not cover: composite keys, per-tenant uniqueness, no shared sequences

- Status: accepted
- Date: 2026-11-11

## Context

RLS filters rows. Several mechanisms look at rows *without* applying policies, and each can answer a question about
another tenant's data. The PostgreSQL documentation warns about covert channels through unique, primary-key and
foreign-key checks ([5.9 Row Security Policies][rls]). Each channel below was reproduced in `RlsPitfallTests` on
PostgreSQL 17 before deciding.

| Channel | What leaks | Reproduced by |
|---|---|---|
| Plain foreign key `customer_id REFERENCES customers(id)` | Tenant A can attach a row to B's invisible customer, and "inserted" vs "FK violation" tells A whether a guessed id exists | `Pitfall_a_plain_foreign_key_bypasses_rls_and_answers_does_this_id_exist` |
| Global unique index on `email` | A unique violation tells A that some tenant has that address | `Pitfall_a_global_unique_index_answers_does_another_tenant_have_this_value` |
| Shared `bigserial` | Gaps in A's ids measure B's insert volume | `Pitfall_a_shared_sequence_leaks_how_much_other_tenants_insert` |
| Error-raising predicates (`1/0` when a hidden value matches) | Would be an oracle if user predicates ran before policies | `User_predicates_cannot_probe_hidden_rows_through_errors` (does **not** leak: policies are security-barrier quals) |
| `pg_stats` (MCV lists, histograms) | Actual column values | hidden by PostgreSQL for RLS tables (tested) |
| `pg_class.reltuples`, `pg_stat_user_tables` | Total row count across tenants | **residual**, tested and documented |

## Decision

- **Composite foreign keys** that include `tenant_id`: `FOREIGN KEY (tenant_id, customer_id) REFERENCES
  customers (tenant_id, id)`, backed by `UNIQUE (tenant_id, id)`. A cross-tenant reference is impossible, and B's real
  id fails exactly like a random id (tested at SQL level and over HTTP: both 422 with the same title).
- **Uniqueness per tenant**: `UNIQUE (tenant_id, email)`.
- **No shared sequences for visible ids**: ids are UUIDv7 generated by the application (`Guid.CreateVersion7()`).
  Human-facing numbers come from a per-tenant counter table under RLS (`app.next_number('order')`), so A's order
  numbers stay consecutive while B inserts (tested).
- **Error mapping is coarse on purpose**: RLS violation 403, FK violation 422 "A referenced record does not exist",
  other tenants' ids 404. The API never says "forbidden" for another tenant's id.

## Consequences

- UUIDv7 ids embed a timestamp. That is fine for this domain; use UUIDv4 if creation time is sensitive.
- The row-count residual (`reltuples`, `n_live_tup`, `EXPLAIN` estimates) remains. Closing it would mean revoking
  catalog access, which breaks tooling. It reveals totals, not tenant data, and is accepted in the threat model.
